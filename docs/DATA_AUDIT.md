## 1. Provenance Classification Taxonomy

To eliminate fabricated data and ensure strict auditability, all data instances across the codebase are classified into one of six categories:
- **`REAL`**: Legitimate, verified static timetables, official station GIS coordinates, and open public datasets (data.gov.in / NDSAP).
- **`DERIVED`**: Mathematically computed values derived from real schedules (e.g. cumulative scheduled distance, timetable scheduled run times).
- **`SIMULATED`**: Real-time telemetry events and perturbation injections generated by deterministic simulation runners.
- **`SYNTHETIC`**: Historical sectional training datasets generated using calibrated statistical distributions with zero temporal leakage.
- **`MOCK`**: Fallback in-memory objects used when external connections (e.g. cloud database) are unconfigured.
- **`PLACEHOLDER`**: Hardcoded UI strings or numbers in React components that must be replaced by dynamic API/database responses.

## 3. Real Data Remediation Strategy

1. **Seed Real Corridor Datasets in Supabase (`supabase/seed.sql`):**
   - Seed verified official timetables for 5 major coaching corridors (50+ stations):
     - `12004` (Lucknow Swarna Shatabdi: NDLS → GZB → ALJN → CNB → LKO)
     - `12951` (Mumbai Rajdhani: BCT → ST → BRC → RTM → KOTA → MTJ → NDLS)
     - `12301` (Howrah Rajdhani: HWH → DGR → ASN → DHN → GAYA → DDU → PRYJ → NDLS)
     - `22436` (Vande Bharat Express: NDLS → CNB → PRYJ → BSB)
     - `12424` (Dibrugarh Rajdhani: NDLS → CNB → PRYJ → DDU → DNR → PPTA → BJU → KIR → NJP → NCB → NBQ → GHY → DBRG)
2. **Implement Unified `TrainDataProvider`:**
   - Abstract database and file queries behind a single `TrainDataProvider` interface, ensuring zero frontend-only hardcoded arrays.
3. **Dynamic Frontend Hydration:**
   - Next.js frontend fetches trains, route geometries, live telemetry, and predictions exclusively through FastAPI REST and WebSocket endpoints.
